## Brief

Decided by Jonas on 2026-10-26, «English, ports for both», relayed by the
agent that runs this loop:

> English copy with Norwegian as a second language, for a general product
> sold internationally.

Context: Tun is going to host a general event-rental product sold beyond
Norway. The change is generic: no client is named in Tun.

What the request asks to be decided and specified, in the relaying
agent's words: the language per tenant, and later per person (English the
default for new tenants; an existing Norwegian tenant stays Norwegian with
no change, or at most a one-line setting); where the copy lives (Tun's own
UI copy, generated forms, error messages, tool descriptions, mail frames
and push copy in catalogues per language; how a client and a module add
their own strings and translations; how a missing one falls back; checked
when compiled where possible); the stored values (module values such as
`tilbud_sendt` and `bekreftet` are Norwegian today: whether they become
English, and if so a migration that rewrites a tenant's database safely,
up and down, idempotent and tested, and what the tools' JSON exposes,
perhaps with the old values as aliases for one version); money (a currency
per tenant, ISO 4217, minor units per currency, formatting per locale, how
existing NOK data reads, exact decimals); dates, times and numbers per
locale, and a time zone per tenant; tool descriptions and MCP schemas in
English or per tenant; mail and push per recipient; tests (a tenant in
English and one in Norwegian, the showcase able to switch language, and a
check that no component leaves a text untranslated); and AGENTS.md's rule
«Code identifiers in English; Norwegian in labels, descriptions and copy»
replaced. As small as the brief allows, with the rest under «Not yet».

Jonas sees gate A himself: the change rewrites stored values of live
tenants.

The contract is the new `spec/i18n.md`, with the specs and module READMEs
it changes (`core.md`, `ui.md`, `mail.md`, `push.md`, `files.md`,

## Decisions

- **Strings as keys, English in the code, catalogues in Lisp.** The
  source text is the key (`(tr "Save")`, gettext's way), and each
  language is a `define-translations` form of pairs. Code stays readable
  with its text at the call site, English is complete by construction,
  there are no invented key names for some two thousand texts, and the
  conversion is mechanical: each Norwegian literal becomes its English,
  and the Norwegian moves into the catalogue.
- **One table per language for all owners, conflicts refused.** The
  conditions (`fail` and the rest) then carry their own text and are
  translated where shown, whoever signalled them, so some 300 call sites
  keep their shape, and a product uses one word for one thing.
  `:context` separates the rare text that needs two translations, and a
  stored value's label tries its `ENTITY.FIELD` context first.
- **Checked when compiled where it can be, by tests where it cannot.**
  `tr` takes only a literal, and a broken translation fails its file's
  compile. Whether every text has a translation needs every system
  loaded, so it is `untranslated-texts` in the suites. The
  pseudo-language finds what a page writes without looking it up, which
  a list of keys cannot; it runs over the module pages as well as the
  components, since a module's page writes copy of its own.
- **The tenant's language only, a setting.** One client codebase can
  serve tenants in different countries, so the language is a setting and
  the code gives only the languages offered and the default. A person's
  own language is later (Jonas: «Later»), so every request writes in the
  tenant's language, which also makes stored copy simple: it is always in
  the tenant's language.
- **Machines get source text.** Tool descriptions and schemas are written
  for models; one contract per Tun version is testable once and the same
  in every tenant; and the agent speaks to its person in their language
  anyway. Only the answer is source text: what a call stores for people
  is in the tenant's language, so a notification an agent causes reads
  like one a person causes. `Accept-Language` on `/api` is later.
- **Business modules renamed outright, without migration** (Jonas:
  «Lean»). No live tenant holds business-module data, so a migration
  engine, input aliases and old paths would be built for no one. Core 2.0
  refuses a 1.x database that holds such data, so none is misread. The
  engine is under «Not yet», for when a live tenant has module data to
  rename.
- **Core's own renames are one explicit migration with a revert.** A
  tenant of core and the dashboard exists, and its database holds the
  three settings and maybe workflows. The migration is written out, not
  declared: it is small, and a general mechanism has one user. It runs
  before the secrets are made, so link tokens and the push key survive.
- **Safety around the one non-additive migration** (Jonas: «All of it»):
  - **The major mark is the migration's record.** The 1.23.1 guard
    (`store.md` §2, item 10, its own loop) writes `core-major-M` under
    `tun-core` in the migrate transaction. 2.0 writes its `core-major-2`
    in the same transaction as its renames, so "migrated" and "marked"
    cannot differ. Nothing is numbered, so nothing varies between
    databases, unlike `ddl-record`'s counted ids. The revert deletes the
    mark, or 1.23.1 would refuse the reverted database for good.
  - **One transaction, in a fixed order:** the higher-major check, the
    business-data refusal, the presence check, the migration with its
    mark, then the additive migrations. A refusal or a failure anywhere
    leaves the database as it was. The secret settings are made after the
    commit, so the renamed secrets are found and kept.
  - **Stop, then start,** because the old process would read renamed
    keys. The check reads `job_processes.lock_key`, since presence keys
    are random, and runs on Postgres only: a SQLite file has one process.
    Under nixploy's blue/green the 2.0 slot then exits 2 while the old one
    runs. That is a safe failure, and §10 gives the stop-then-deploy
    steps.
  - **The revert is one transaction too.** It refuses when 2.0 has
    written business-module rows, which 1.x could not read, and it
    deletes every `locale.*` row, an admin's included, since 1.x has none.
  - **The preflight refuses** on every store while the mark is present,
    before reading its registry, since the registry comparison works on
    SQLite only.
  - **A backup comes first,** and the revert runs with the server stopped
    as a one-off Podman container of the same image, with the target's
    SOPS file: nixploy's `run` uses the running container, which is
    stopped by then.
- **What counts as business-module data is decided by `schema_history`,
  not by table names,** for tables. A client may have its own
  `customers` table, as the live client does, so a table counts only
  when a business module's `create_TABLE` row made it. Rows a business
  module keeps in core's tables count too (Jonas: «Refuse them too»):
  its settings, its workflow kinds and its job kind, listed by their 1.x
  names, since the 2.0 code that checks no longer knows those names. A
  loaded inbox makes its secret at start, so such a tenant is refused
  even with no inquiry: it would otherwise lose the secret its inbound
  mail is signed with. A `create_` row from before modules has no
  module, and counts by its table's name, the one case where a client's
  own table of a module's name would be refused.
- **Fixtures from core 1.23.1,** since live tenants will be on it with a
  `core-major-1` mark. A copy without the mark stands for an older
  database. They can be made only once the guard is merged, which is also
  when this loop merges main.
- **A 1.x database keeps its locale without the client's help.** The
  migration records `nb`, `NOK` and `Europe/Oslo` on a database 1.x
  wrote, since that is what its data means. A client that forgets the
  `:locale` line gets English test databases, which its suite shows, but
  never a production tenant whose kroner read as euros.
- **What history holds is not rewritten,** and id prefixes, opaque keys
  inside records and link-token purposes stay: changing them would
  invalidate references, plans' fingerprints and links, for no reader.
- **Money is an integer of minor units in a `money` field named
  `…_minor`.** `_ore` names a Norwegian unit, and an agent reading a
  bare `total` of 1245000 could take it for major units, a hundredfold
  error; `_minor` (ISO 4217's term) says what it is, and the compiler
  enforces the name. One currency per tenant, fixed while amounts exist,
  because records carry no currency of their own. Forms read amounts
  with integers and strict grouping, so `0,29` is 29 and `12,50` on an
  English tenant is a question, not 1250.
- **Time zones by rule, Europe first, no time-zone database.** The
  kernel's existing summer-time rule generalised to an offset; it covers
  the EU, EEA and UK exactly, with no data file to keep current. A change
  of zone runs no occurrence twice: an occurrence runs only when it is
  later than the last that ran.
- **Formats.** English dates are `21 Oct 2026`, which no British or
  American reader misreads, with a 24-hour clock; money follows each
  language's common conventions (Unicode CLDR's, in one table).
- **Defaults `en`, `EUR`, `UTC`.** Neutral for a product sold abroad; a
  client names its own.
- **Specs keep quoting Norwegian.** The specs and READMEs quote hundreds
  of messages in Norwegian; they now count as the `nb` translations
  (`spec/i18n.md` §3.8) rather than being rewritten in this change. The
  identifiers they name are renamed.
- **The test tenants.** The kernel's suite runs English, the new default.
  The test client stays Norwegian, as a 1.x client that added the one
  line, so its suite proves a Norwegian tenant still works. The showcase
  becomes English with a Norwegian catalogue, the client side of the
  mechanism, and switches language on «Settings».
- **The dashboard keeps its old paths as 301s.** It is the one module a
  1.x tenant uses, three redirects are cheap, and bookmarks keep working;
  a test that expected 200 at `/jobber` is updated.
- **`docs/architecture.md`, `docs/client-api.md` and the template of
  `tun new`** follow in Build: they describe the code rather than promise
  behaviour.
- **Core 2.0.0, not 1.24.0.** The change breaks stored setting keys and
  workflow statuses, the values and field names in tools' JSON, tool
  names, public Lisp functions (`order-total-ore`), and the default
  language. Each module's core range moves to `>= 2.0.0, < 3.0`, so no
  1.x client builds against it by accident.

# Languages, money and time

Status: specified 2026-10-28, for core 2.0.0. How a tenant speaks its
language, counts its currency and keeps its time. Tun's copy is written in
English, and Norwegian (bokmål) is a second language in catalogues. Each
tenant has a language, a currency and a time zone. The identifiers Tun
stores are English.

Decided by Jonas on 2026-10-26: «English, ports for both». Tun is to host
products sold beyond Norway, so its copy is English first and Norwegian
second, and nothing in it assumes Norway.

## 1. In short

- **Copy.** Every text Tun writes for people is written in English in the
  code and translated in a catalogue per language (§3). A text without a
  translation shows the English.
- **Per tenant.** A tenant's language, currency and time zone are settings
  (§2, §5, §6). Pages, and the copy Tun stores for people (notifications,
  notes, mail, push), are in the tenant's language.
- **Machines get source text.** `tools/list`, `registry_describe` and the
  error documents on `/mcp` and `/api` are Tun's source text, untranslated,
  on every tenant (§7).
- **English identifiers.** The business modules' status words, kinds,
  keys, tool names, field names and paths are renamed to English in core
  2.0, outright (§4.2). Core's own Norwegian keys and statuses are renamed
  by one migration, with a way back (§4.4). Core 2.0 refuses a 1.x
  database that holds business-module data (§4.3).
- **Money** is an integer of the tenant's currency's minor units, in a
  field whose name ends `_minor` (§5).
- A tenant from before 2.0 that holds no business-module data, such as a
  client of core and the dashboard, stays Norwegian, in kroner and in
  Norwegian time (§4.4, §10).

## 2. Languages

### 2.1 The languages

| Code | Language |
|---|---|
| `en` | English. The language Tun's own copy is written in. |
| `nb` | Norwegian bokmål. Tun ships its catalogue (§3.2). |

Codes are BCP 47 tags. A page's `<html lang>`, a mail's frame and the
app's manifest carry the code of the language they are in.

### 2.2 What a client declares

```lisp
(define-application rental-application ()
  (:locale :languages ("en" "nb") :currency "EUR" :time-zone "Europe/Berlin"))
```

| Option | Means | Default |
|---|---|---|
| `:languages` | The languages a tenant of this client may be set to, without repeats, each one of §2.1's. The first is a new tenant's. | `("en" "nb")` |
| `:source-language` | The language the client's own copy is written in (§3.4). One of `:languages`. | the first of `:languages` |
| `:currency` | A new tenant's currency, a code of §5.1. | `"EUR"` |
| `:time-zone` | A new tenant's time zone, a name of §6.1. | `"UTC"` |

Any other option, or a value outside these, is an error when the form is
compiled, as `(:web-app ...)`'s are.

### 2.3 The tenant's language

Core declares the setting `locale.language`, whose value is one of the
application's `:languages`, the first by default. An admin changes it
with `settings_set` or on «Settings»; the next request is in the new
language. A value the application does not offer is `invalid_input`. A
stored value the application no longer offers (a client that dropped a
language) reads as the first of `:languages`.

### 2.4 The language of a request

- Every request, job, workflow run, schedule and trigger is in the
  tenant's language: what it shows, and what it stores for people to
  read (§3.5).
- What is answered to a machine is source text (§7).
- `(current-language)` is the language being written in. `(with-language
  (CODE) BODY...)` writes BODY in CODE, one of §2.1's.

A person's own language is under «Not yet» (§11).

## 3. Copy and catalogues

### 3.1 Writing copy

Copy in code is written in the owner's source language: English in core
and the modules, `:source-language` in a client.

- **`(tr TEXT ARG...)`**, in the TUN package, is TEXT in the current
  language, used as a `format` control with ARGs: `(tr "~d files
  attached" n)`. TEXT is a literal string, or `(STRING :context WORD)`
  for a text that needs two translations, such as `("Open" :context
  "verb")`. Anything else as TEXT is an error when the form is compiled.
- **Conditions carry their text.** `fail`, `fail-with-details`, `reject`,
  `reject-as` and `input-error` keep their control string and arguments,
  and the message is made where it is shown: in the current language on a
  page and in what Tun stores for people, as source text to a machine
  (§7). `(fail :conflict "The board has changed. Reload it.")`.
- **A stored value as an argument is passed as its label**, `(label
  "order" "status" status)`, which is written in the language of the
  message it is in: `(fail :invalid-transition "The order is ~a and
  cannot become ~a" (label "order" "status" from) (label "order" "status"
  to))` reads «The order is Quote sent and cannot become Completed» to a
  machine and «Ordren har status Tilbud sendt og kan ikke bli Ferdig» on
  a Norwegian page. A raw value never appears in a message.
- **Definitions translate where they are shown.** The texts a definition
  gives as data are looked up when a page, a mail or a form shows them:
  an entity's `:label`, a field's and a parameter's `:label` and
  `:description`, an operation's `:title`, a page's and a resource's
  `:title`, a setting's `:description`, a workflow's and a template's
  `:label`. An operation's `:description` is for agents only, and is
  never translated.
- **A stored value's label** is the value with its first letter
  capitalised and `_` as spaces (`quote_sent` is «Quote sent»). It, and a
  field's own label, is looked up with the context `ENTITY.FIELD` first,
  then without one, since one word may need two translations:
  `(("Cancelled" :context "order.status") "Avlyst")` beside `("Cancelled"
  "Avbrutt")`.
- A text from the user or the data (a name, a note, a customer's
  message) is never looked up.

### 3.2 Catalogues

```lisp
(define-translations "nb"
  ("Save" "Lagre")
  ("~d files attached" "~d filer lagt ved")
  (("Open" :context "verb") "Åpne")
  ("Quote sent" "Tilbud sendt"))
```

- A catalogue is a `define-translations` form in a file of its owner's
  system, loaded with it: `nb.lisp` in a module or a client, and the files
  under `src/i18n/` in core. An owner may spread its translations over
  several forms.
- Each entry is a source, as `tr` takes it, and its translation. A
  translation holding a `~` directive is compiled as a `format` control
  where it is defined, so a broken one is an error then.
- The catalogues of every owner make one table per language. Two entries
  for one source and context with different translations are refused
  when the second is loaded, naming both owners: one product uses one
  word for one thing.

### 3.3 Fallback

A text is shown in the current language when the catalogue has it, and
as written otherwise: a missing Norwegian translation shows the English,
never a key or nothing.

### 3.4 A client's copy

A client writes its copy in its `:source-language` and ships a catalogue
for each other language it offers. A client written in Norwegian that
offers only Norwegian, `(:locale :languages ("nb"))`, needs none: its
texts are shown as written, and Tun's own in Norwegian from Tun's
catalogue.

### 3.5 Copy stored for people

What Tun stores for a person to read later is written in the tenant's
language when it is stored, whoever caused it: an agent over `/mcp`, a
system over `/api`, a job or a page. This holds for notifications, a
workflow's or a job's note, a ledger's reason Tun writes, mail and push
notifications. It is stored as text and not translated again. Recorded
errors and the log line are for developers and agents, and keep the
source text.

### 3.6 Scripts, the worker and the specimen

- The components' script and the service worker hold no copy. A text a
  script shows, such as the board's «Moved … to …», is in the markup the
  server rendered, in the page's language. The worker's text for a push
  without data is written into `/sw.js` in the tenant's language.
- The specimen (`/ui`) shows each example in the current language. A
  component's `:doc`, an example's title and the specimen's own chrome
  are developer documentation, in English, and not translated.

### 3.7 Checks

- `(untranslated-texts LANGUAGE &key owner)`, in `tun.test-support`,
  lists every text an owner has whose source language is not LANGUAGE
  and that LANGUAGE's catalogue lacks, with where it is: `tr` and the
  refusals with a literal text (recorded when compiled), the texts of
  §3.1's definitions, and the labels of the values of every enum field
  and parameter. `(unused-translations LANGUAGE &key owner)` lists
  catalogue entries no text uses.
- Core and every module have none of either for `nb`. A client's suite
  made by `tun new` checks its own texts for each language it offers.
- **The pseudo-language.** `qps`, for tests only and never a tenant's,
  shows every looked-up text as `⟦TEXT⟧`. Rendered in it, a page shows no
  text, and no `aria-label`, `title`, `placeholder` or `alt`, with a
  letter outside `⟦⟧`, except the strings of the records it shows and
  those its caller passed: a text written without being looked up is
  found. It is rendered over every component example (the example's own
  strings excepted), the kernel's pages, and the generated and module
  pages of the test client with its scenario's records.

### 3.8 Copy quoted in specs

Where a spec or a module's README quotes Tun's copy in Norwegian, such as
«Flytt til», it quotes the `nb` translation; the English is the source in
the code. A test checks the copy of the language it runs in.

## 4. Identifiers

### 4.1 The rule

Identifiers are English: the status words, kinds and modes Tun stores,
setting keys, template keys and variables, workflow kinds, tool and
entity names, field names, the system's actor names, and the paths of
module pages. A value's label (§3.1) is what a person reads.

Not renamed, since they are opaque or already handed out: id prefixes
(`fil_`, `hen_`, `fak_`), opaque keys inside records (a checklist item's
`source_key`, `lager:…`; a plan source's, `krav:…`) and link-token
purposes (`avmeld`, `tilbakemelding`).

### 4.2 The business modules: renamed outright

Every module but `dashboard` names its identifiers in English from core
2.0 (§4.8). There is no migration of their data, no old name read as
input and no old path served: no live tenant holds business-module data,
so nothing has to move, and a database that holds any, in a module's
tables or in core's, is refused (§4.3).
Their READMEs give only the new names.

### 4.3 A 1.x database with business-module data is refused

**Which databases.** A database is *new* when its `schema_history` shows
no table created: no `create_` row, one whose migration id ends
`_create_TABLE`, and no row from before modules (no module and no
migration id) whose statement is a `CREATE TABLE`. (A fresh SQLite file
already has `core_0001_schema_history_modules` when this is checked,
which is not a `create_` row. The memory store's database is new at every
start, and its migration writes no mark.) A database that is not new and
has no `core-major-2` mark (§4.4) was written by core 1.x; one from core
1.23.1 on also has the mark `core-major-1` (`store.md` §2, item 10).

**Business-module data.** The business modules are every module but
`dashboard`, whose definitions count as core's. A 1.x database holds
business-module data when it has any of these rows, by their 1.x names:

- **A row in a table a business module created:** a table whose `create_`
  row in `schema_history` names that module. Those tables in core 1.22
  and 1.23 are:

  | Module | Tables |
  |---|---|
  | calendar | `calendar_events` |
  | catalog | `products`, `recipes`, `choice_groups`, `catalog_changes` |
  | customers | `customers` |
  | inbox | `henvendelser` |
  | inventory | `articles`, `inventory_movements`, `transfers`, `consumption_commands`, `stock_levels`, `reservations` |
  | invoicing | `invoices`, `invoice_send_intents` |
  | messaging | `messages`, `deliveries` |
  | notifications | `notifications` |
  | orders | `orders`, `bookings`, `quotes`, `checklist_items`, `plans`, `plan_impacts`, `plan_impact_queue` |
  | reviews | `reviews` |
  | staffing | `employees`, `assignments`, `assignment_overrides`, `unavailabilities`, `work_sessions` |
  | warehouse | `tasks`, `task_events` |

  A row with no module and no migration id (a database from before
  modules, whose rows gained the columns empty) counts as a business
  module's when the table its `CREATE TABLE` statement creates is in
  this list.
- **A row of `settings`** whose key a business module declares or reads:
  `innboks.hemmelighet` (inbox), `avsender.navn`, `avsender.epost`,
  `avsender.svar_til` (messaging), and `tilbud.gyldig_dager` (orders) and
  `anmeldelse.url` (messaging), which a client declares for the module.
  A loaded inbox makes its secret at start, so a tenant that loaded the
  inbox counts even with no inquiry.
- **A row of `workflows`** of a business module's kind: `tilbud_utløp`
  and `katalog_endring` (orders), `leveranse_vakt` (messaging), and
  `tilbud_påminnelse` and `neste_år`, which a client defines for orders.
- **A row of `jobs`** of a business module's job kind: `send_delivery`
  (messaging).

A client's own tables and core's other rows never count, whatever they
hold and whatever they are called: a client's own `customers` table was
created by `client`, not by the customers module. The one exception is a
database from before modules, whose history does not say who created a
table: there a client's table with a business module's name, holding
rows, counts as that module's. Such a database is
refused at start (§4.4, step 2): the server exits 2, having changed
nothing, with «This database holds data of the module MODULE written by
core 1.x. Core 2.0 renamed the modules' stored identifiers and does not
migrate them (spec/i18n.md §4.3). Keep this tenant on core 1.x.» A
migration of such data is under «Not yet».

### 4.4 Core's migration, and the order of a start

Core renames its own Norwegian keys and statuses on a database core 1.x
wrote:

| Old | New | In |
|---|---|---|
| `lenker.base_url`, `lenker.hemmelighet`, `push.hemmelighet` | `links.base_url`, `links.secret`, `push.secret` | the stored settings' keys, their values kept |
| `planlagt`, `utført`, `avbrutt`, `feilet` | `planned`, `executed`, `cancelled`, `failed` | `workflows.status` |

and stores the locale such a database was written in: `locale.currency`
`NOK`, `locale.time_zone` `Europe/Oslo`, and `locale.language` `nb` when
the application offers it.

**Its record is the major mark.** The migration has no record of its own:
the `core-major-2` row the major guard writes (`store.md` §2, item 10:
`module` `tun-core`, `migration` `core-major-2`) is written in the same
transaction as the migration, so a database has the mark exactly when it
has been migrated. Nothing is numbered, so nothing differs between
databases.

**The order of a start of 2.0.** Each start opens the store's migrate
transaction (`store.md` §2) and, in it, in this order:

1. **A higher major** (`core-major-3` or above) is refused, as the guard
   refuses it (`newer-database`).
2. **Business-module data** in a 1.x database is refused (§4.3).
3. **Another process** using a 1.x database is refused (§4.5).
4. **The migration**, on a 1.x database: the renames, the `locale.*`
   settings and the `core-major-2` mark. On a new database (§4.3) only the
   mark is written, with nothing to rename and no `locale.*` stored, so it
   takes the application's defaults. On a database that has the mark,
   nothing.
5. **The additive migrations**, as every start runs them.
6. Then, after the commit, the secret settings are made where they are
   missing, so `links.secret` and `push.secret` keep the values they had
   under their old keys: link tokens and the push key do not change.

- **All or nothing.** The steps are one transaction. A refusal in steps 1
  to 3, or a failure anywhere, rolls it back: the database is as it was,
  without the mark, and the server exits non-zero. The next start begins
  again at step 1.
- **How a refusal ends.** Each refusal of steps 1 to 3 is a condition
  signalled inside the migrate transaction, as the guard's
  `newer-database` is: the transaction unwinds, `open-application` closes
  the store in its cleanup, and `main` prints `NAME: MESSAGE` on stderr
  and exits 2.
- **Once.** A database with the mark is not migrated again; run again over
  renamed data, step 4 would change nothing, since it rewrites only the old
  keys and statuses.

### 4.5 Stop, then start

On Postgres, step 3 refuses with exit 2 while another process uses the
database: a row of `job_processes` whose `lock_key` another process holds
(`store-present-p`, `store.md` §3; the keys are random, so the check reads
them from the table). The migration renames what an older process reads,
so the move to 2.0 stops the old server first and then starts the new one,
rather than running both for a moment as a blue/green switch does (§10).
On SQLite a database has one process, which is this one, and nothing is
checked.

### 4.6 The way back

- **Revert.** `SERVER --revert-to-core-1`, with `--db DB` or, without
  it, `DATABASE_URL`, as serving reads them. In one write transaction, all
  or nothing, it:
  1. refuses, exit 2, on a database without the `core-major-2` mark, a
     higher major's mark (saying that it does not revert it, not that it
     does not start), or (on Postgres) while another process uses it, as
     §4.5 checks;
  2. refuses, exit 2, when it holds business-module data as §4.3 counts
     it, under 2.0's names: a row in a business module's table
     (`inquiries`, not `henvendelser`), a `settings` row of `inbox.secret`,
     `sender.name`, `sender.email`, `sender.reply_to`, `quotes.valid_days`
     or `customer_review.url`, a `workflows` row of `quote_expiry`,
     `catalog_change`, `delivery_watchdog`, `quote_reminder` or
     `next_year`, or a `jobs` row of `send_delivery`. Such rows were
     written by 2.0, in names 1.x cannot read;
  3. renames back what §4.4 renamed;
  4. deletes every `locale.*` setting, those an admin set included, since
     1.x has none;
  5. deletes the `core-major-2` mark, so core 1.23.1 opens the database
     again;
  6. commits and exits 0 without serving.

  A failure anywhere leaves the database as it was, and it exits
  non-zero. The database is then as core 1.x left it, but for what 2.0
  added that 1.x ignores: additive columns and tables, jobs, job
  processes and audit entries.
- **The preflight.** `SERVER --rollback-preflight REGISTRY`, with `--db`
  or, new in 2.0, `DATABASE_URL` without it, refuses with exit 3 on every store while the database
  has the `core-major-2` mark, naming `--revert-to-core-1`. It does so
  before REGISTRY is read: any path gets this answer. After the revert it
  checks the registry as before (`core.md` §6.4). With neither `--db` nor
  `DATABASE_URL` it refuses with exit 2, naming both.
- **Core 1.23.1** refuses to start on a database with a `core-major-2`
  mark (`store.md` §2, item 10). Clients move to 1.23.1 before 2.0, so a
  rollback that forgets the revert cannot start on renamed data; the
  revert removes the mark, so one that does the revert can.

### 4.7 Evidence for the migration

`tests/fixtures/core-1.23.1/` holds two databases as core 1.23.1 wrote
them, each dumped from Postgres and from SQLite, each with its
`core-major-1` mark: one with core's data only (the three settings, a
workflow of a core kind in each status, accounts, mail) and a client's
own `customers` table full of rows; one that also holds business-module
records; and one of a client that loaded the inbox and holds no inquiry,
only the inbox's secret. A test takes the mark out
of a copy, to stand for a database from core 1.22 or earlier.

## 5. Money

### 5.1 Currencies

A tenant's currency is the setting `locale.currency`, an ISO 4217 code
of this table; the application's `:currency` by default.

| Code | Currency | Minor digits |
|---|---|---|
| `NOK` | Norwegian krone | 2 |
| `SEK` | Swedish krona | 2 |
| `DKK` | Danish krone | 2 |
| `ISK` | Icelandic króna | 0 |
| `EUR` | Euro | 2 |
| `GBP` | Pound sterling | 2 |
| `USD` | US dollar | 2 |
| `CHF` | Swiss franc | 2 |
| `PLN` | Polish złoty | 2 |

Another currency is a line in this table and its formats (§5.4).

### 5.2 Amounts

- An amount is an integer count of the currency's minor units: 12 450,00
  kr is `1245000`, 12 450 ISK is `12450`. Never a float; arithmetic on
  amounts is on integers, and rationals where a share is taken. An amount
  is at most 2⁵³ − 1 minor units, so JSON carries it exactly.
- **The `money` field type** holds one, in a field or a parameter whose
  name ends `-minor` (`total-minor`, JSON `total_minor`); a `money` field
  or parameter named otherwise is an error when the definition is
  compiled. Its JSON Schema is an integer whose description names the
  tenant's currency and its minor digits.
- A tenant has one currency. Amounts are not converted, and records do
  not carry a currency of their own.

### 5.3 Changing the currency

`settings_set locale.currency` is `conflict` while any stored record of an
entity with a `money` field exists: the amounts would change their worth.
On a tenant with none, it changes.

### 5.4 Writing and reading amounts

A page writes an amount in the tenant's language:

| | `en` | `nb` |
|---|---|---|
| Digits | groups of three by `,`, decimals after `.` | groups of three by a no-break space, decimals after `,` |
| Negative | `-` before the symbol or code | `−` (U+2212) before the digits |
| Symbol | before the amount for EUR `€`, GBP `£`, USD `US$`; else the code and a no-break space | after the amount and a no-break space: `kr` for NOK, `€` for EUR, `£` for GBP; else the code |
| Examples | `€12,450.00`, `NOK 12,450.00`, `ISK 12,450`, `-€5.00` | `12 450,00 kr`, `12 450,00 €`, `12 450 ISK`, `−5,00 kr` |

A form takes an amount as a person writes it, in major units, with at
most one sign and one decimal mark:

| | `en` | `nb` |
|---|---|---|
| Decimal mark | `.` | `,` or `.` |
| Groups | `,` or a space, between groups of exactly three digits after the first | a space or a no-break space, the same way |
| Taken | `12,450.50`, `12450.50`, `0.29` | `12 450,50`, `12450,50`, `12450.50`, `0,29` |
| Refused | `12,50`, `1,2345.00`, `12.450.50`, `1.2.3` | `12 450,505`, `1 23,00`, `12,450,50` |

It is read with integers into minor units, exactly: `0,29` is 29 øre,
never 28. More decimals than the currency has (any for ISK), a mark or a
group where the table does not allow one, a letter, or more than 2⁵³ − 1
minor units, is `invalid_input` on the field. The control shows the
currency beside it. Over MCP and `/api` an amount is the integer.

## 6. Dates, times and numbers

### 6.1 Time zones

A tenant's time zone is the setting `locale.time_zone`, a name of this
table; the application's `:time-zone` by default. Tun keeps no time-zone
database: each zone is an offset from UTC and whether it keeps European
summer time, which runs from the last Sunday of March 01:00 UTC to the
last Sunday of October 01:00 UTC (exclusive), one hour ahead.

| Name | Offset | European summer time |
|---|---|---|
| `UTC` | +00:00 | no |
| `Atlantic/Reykjavik` | +00:00 | no |
| `Europe/London`, `Europe/Dublin`, `Europe/Lisbon`, `Atlantic/Faroe` | +00:00 | yes |
| `Europe/Oslo`, `Europe/Stockholm`, `Europe/Copenhagen`, `Europe/Berlin`, `Europe/Amsterdam`, `Europe/Brussels`, `Europe/Luxembourg`, `Europe/Paris`, `Europe/Madrid`, `Europe/Rome`, `Europe/Vienna`, `Europe/Zurich`, `Europe/Warsaw`, `Europe/Prague`, `Europe/Budapest` | +01:00 | yes |
| `Europe/Helsinki`, `Europe/Tallinn`, `Europe/Riga`, `Europe/Vilnius`, `Europe/Athens`, `Europe/Sofia`, `Europe/Bucharest` | +02:00 | yes |

The rule is today's, applied to every year, which is all Tun needs: it
writes no local time before 2026.

- **Local time** is the tenant's: "today", a local date or time of day
  (`core.md` §2.1), a whole-day interval, the instant a local date and
  time stand for (`to_utc`, with its ambiguous and non-existent times,
  `core.md` §2.2), and a schedule's cron time (`jobs.md` §8).
- **Changing the zone** changes those from the next request on; stored
  instants are UTC and stay as they are. A schedule's next occurrence is
  its cron time in the new zone. An occurrence runs only when its instant
  is later than that of the last one recorded, so a change never runs an
  occurrence twice, nor one earlier than the last. A change that puts an
  occurrence of the new zone between the last one and now runs it once, at
  once, as a missed occurrence does (`jobs.md` §8, `:catch-up`): moving a
  daily 07:00 from `Europe/London` to `Europe/Oslo` at 06:30 London time
  runs today's 07:00 Oslo (06:00 UTC) then.

### 6.2 Formats

| | `en` | `nb` |
|---|---|---|
| A date | `21 Oct 2026` | `21.10.2026` |
| A time of day | `14:32` | `14:32` |
| An instant, in the tenant's zone | `21 Oct 2026, 14:32` | `21.10.2026 kl. 14:32` |
| A number | `12.5` | `12,5` |
| Yes and no | `Yes`, `No` | `Ja`, `Nei` |

Month and weekday names come from the catalogue. `date-text`,
`timestamp-text`, `number-text` and `money-text`, in the TUN package,
write a value so for a client's page. A form reads a decimal with the
language's decimal mark, and in `nb` with `.` too.

## 7. What machines are answered

  English for Tun's own, a client's own definitions in its source

  "currency", "minor_digits", "time_zone"}`.

  `(:instructions ...)`.

## 10. Moving a client from 1.x

What a client of core and the dashboard does (a tenant with
business-module data stays on 1.x, §4.3):

1. Move to core 1.23.1 first, and deploy it (§4.6).
2. `tun update` to a Tun with core 2.0.0. Every module ships with the
   range `>= 2.0.0, < 3.0`.
3. A client written in Norwegian adds one line to `define-application`,
   so that its new databases (tests, previews) are what its tenant is:
   `(:locale :languages ("nb") :currency "NOK" :time-zone "Europe/Oslo")`.
   Its tenant's database needs nothing more: the migration stores
   `locale.language` `nb` when the application offers Norwegian (§4.4),
   which this line does, as does leaving `(:locale ...)` out (§2.2). A
   client whose `:languages` leaves `nb` out gets no `nb` stored, and its
   tenant reads English.
4. Its tests are updated where they name what 2.0 renamed (§4.8): a test
   that expects `/jobber` to answer 200 now gets 301 to `/jobs`, and one
   that reads `lenker.base_url` reads `links.base_url`. The build names
   each renamed function it calls as undefined.
5. `bin/test`, then deploy, with the target offline for the switch.
   nixploy deploys blue/green: a plain `nixploy deploy` starts the 2.0
   slot while the 1.x slot runs, and the 2.0 server exits 2 (§4.5). That
   is the expected, safe failure: nothing has changed, the deploy fails
   its health check, and the 1.x slot goes on serving. Instead:
   1. `nixploy stop --target TARGET`, which takes the route away and
      stops the 1.x container, so nothing writes after the dump;
   2. back up the database on the host (`deploy.md` §4: `sudo systemctl
      start postgresqlBackup-DATABASE` on NixOS), and copy the dump out of
      `/var/backup/postgresql`, where the nightly rotation replaces it
      within two nights;
   3. `nixploy deploy --target TARGET`, which starts the 2.0 slot alone;
      it migrates at its first start (§4.4) and serves.
6. To go back, with the server stopped (`nixploy stop --target TARGET`),
   run the 2.0 image once on the host with the target's secrets. nixploy
   has no one-off container (its `run` uses the running one), so run it
   with Podman, as the target's nixploy `user` (USER, whose rootless
   Podman holds the images), the image being the 2.0 one nixploy loaded
   (`podman images` as that user), and `secrets/TARGET.env` standing for
   the file the target's `secrets` names (`deploy.md` §3):

   ```
   sops -d secrets/TARGET.env | ssh USER@HOST \
     'f=$(mktemp) && cat > "$f" && podman run --rm --network host \
        --env-file "$f" IMAGE --revert-to-core-1; s=$?; rm -f "$f"; exit $s'
   ```

   The image's entrypoint is the server (`deploy.md` §2), which reads
   `DATABASE_URL` from that file. Then deploy the client at its 1.23.1
   pins. Or restore the dump of step 5.2 into a fresh database.
